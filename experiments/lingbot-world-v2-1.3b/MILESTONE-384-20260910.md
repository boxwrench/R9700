# LingBot World 1.3B — 384×672 Interactive Latency Milestone

Date: 2026-09-10

This document records the three bounded experiments run after the 2.81 s steady-state baseline. No production code was modified during the experiments; harnesses lived under `/tmp/exp*.py` and results under `/ai/outputs/lingbot-exp/`.

## Outcome

1. **Clean-KV scheduling:** retain decode-first serial ordering (B). At 464×832, first presentation improved from 2.781 s to 2.480 s (−301 ms) with identical accepted x0 and identical final KV state. Same-GPU overlap (C) was rejected: zero kernel overlap and P95 3.743 s.
2. **Resolution:** select native **384×672 executed geometry**. The requested 384×688 area target maps to 384×672 for this 16:9 input/upstream arithmetic. End-to-end A-order latency improved from 2.806 s to 1.712 s (−39.0%) with acceptable world behavior through nine KV evictions.
3. **Exact backend audit:** negative result. Both DiT attention and FP16 VAE are already on healthy implementation paths. No single exact optimization cleared the 150 ms application-level threshold, so none was implemented.

## Experiment 1 — clean-KV scheduling

All five DiT forwards write the same KV slots. Denoising passes leave noisy K/V; the clean t=0 pass overwrites them. Index fills are idempotent within an action; eviction roll happens once on the first forward and costs approximately 13–23 ms. Manually splitting denoise and clean execution is bit-identical to the accepted full step.

### A — clean → VAE

- first presentation: 2.781 s
- state ready: 2.781 s

### B — VAE → display → clean

- first presentation: **2.480 s**
- state ready: 2.785 s
- improvement in perceived first-paint latency: **301 ms**
- x0 and final KV state: bit-identical to A across trials

B changes scheduling only; it does not reduce total work or steady-state cadence. A user pressing again at first paint still waits for the clean commit barrier.

### C — VAE || clean on two streams

Rejected.

- median first presentation: 2.792 s
- P95: 3.743 s
- post-denoise concurrent wall: 1.541 s
- corresponding serial sum: 1.536 s
- observed GPU kernel overlap: **zero**
- two-action completion: 5.83 s vs 5.57 s baseline

The device time-slices/serializes rather than usefully overlapping these workloads. Do not retry same-GPU VAE/clean-pass overlap unless the workload or software stack changes materially.

## Immediate-next-input behavior

End-state equality means the following action behaves identically regardless of predecessor ordering once the clean commit is complete.

The decode-first B ordering improves feedback but not the fundamental feedback-loop cadence. Track both:

- keypress → first action-conditioned RGB
- keypress → next DiT-ready persistent state

These are distinct product metrics.

## Experiment 2 — native 384×672

The intended 384×688 area target executes as **384×672** for this 16:9 input.

Derived geometry:

- latent: 48×84
- tokens/frame: **1008**
- KV local capacity: **18,144 tokens**
- KV memory: approximately 3.1 GiB

Conditioning was freshly encoded. Plücker rays, intrinsics, KV state, and VAE state were constructed natively; no conditioning tensor resize shortcut was used.

Steady-state over the final eight actions of a 27-action regression:

- DiT: **0.881 s**
- first/full A-order: **1.712 s**
- P95: **1.714 s**
- VAE: **0.831 s**
- peak VRAM: **10.21 GiB**

Relative to 464×832:

- total: **−39.0%**
- DiT: **−43.7%**
- VAE scales almost exactly with pixel area: 0.831 / 1.242 = 0.669 vs pixel ratio 0.668

No new VAE solver cliff appeared.

### Quality / persistence

The same 27-action script included turns, left reversal, back reversal, and nine post-eviction actions.

Observed:

- all outputs finite
- no frozen frames
- seam ratio 1.033 (464 reference 1.019)
- eviction exactly at action 18
- continuous unit translation / zero-rotation pose steps where expected
- strong correct right-turn displacement
- strong opposite back-reversal displacement
- single-step left-turn response weaker at 384 than 464, flagged for future control-quality review
- coherent lake/tree/mountain geometry late in the session
- expected modest loss of fine detail

Literal pixel revisitation was not tested by this path because 8-degree increments did not revisit the same pixels.

**Selected native geometry: 384×672.**

## Experiment 3 — exact backend audit at 384×672

### DiT

Full-context 5-forward time: approximately **0.89 s**.

Per-forward context growth:

- short: ~0.100 s
- intermediate: ~0.135 s
- full: ~0.171–0.183 s

Approximate decomposition:

- context-independent cost: ~0.50 s/action
- context-dependent cost: ~0.38 s/action
- 30 transformer blocks: ~0.840 s
- self-SDPA: **~0.412 s (45%)**
- cross-SDPA: ~0.019 s (2%)
- RoPE: ~0.044 s (5%)
- embeddings: ~0.006 s / five forwards
- first-forward eviction roll: ~13 ms

Actual self-attention backend:

- PyTorch SDPA
- **AOTriton efficient-attention Triton kernel** on ROCm
- BF16
- Lq=1008
- Lk=18144
- x `[1,1008,1536]`
- K cache `[1,18144,12,128]`
- contiguous layout
- local window enforced by slicing
- `causal=False`
- no materialized attention-score tensor
- no sink/history/current concatenation copies
- one clone per evicting action

Backend bake-off:

- default / flash-only / memory-efficient-only: ~0.172 s/forward, same effective kernel
- math-only: **1.524 s/forward (8.9× worse)**

Conclusion: current attention path is already fused and healthy enough that no supported exact switch on this machine provides a >=150 ms application win.

### FP16 VAE

384×672 wall: approximately **0.83 s**.

- Conv3d: ~91% / 0.757 s
- RMSNorm: ~4%
- everything else: ~5%

By input temporal extent:

- T=4: ~83%
- T=2: ~6.5%
- T=1: ~1.5%

Ideal first-prefix opportunity from the measured stage distribution is only approximately **66 ms (~8%)** before accounting for implementation overhead. A prefix rewrite is therefore not justified at this resolution under the existing threshold.

Dominant FP16 convolutions run around 7.6–27 TFLOP/s on the healthy implicit-GEMM path. Temporal split 1/2/3 was effectively identical (~810–814 ms), and MIOpen FAST vs unset was effectively identical (~817/819 ms).

An early standalone convolution result suggesting a 2× solver gap was retracted after root cause: constructor arguments produced an invalid comparison. Its dtype/solver sub-conclusion is discarded. The accepted production FP16 result remains the earlier validated Phase 2 result.

## Disqualification ledger at 384×672

Measured opportunities that do **not** meet the current exact-optimization threshold:

| Candidate | Result / ceiling |
|---|---:|
| SDPA backend switch | ~0 ms |
| head-major KV layout | ~16 ms/action |
| VAE solver/split alternatives | ~0 ms |
| first-prefix VAE | ideal ceiling ~66 ms before overhead |
| embedding hoist | ~6 ms |
| KV eviction roll | ~13 ms |
| RoPE FP32 removal/change | ~44 ms but inexact |
| clean-pass final tail | ~50 ms class; previously closed as low-value/correctness-sensitive |
| launch-gap graph/compile opportunity | ~60 ms class; below current threshold and maintenance risk |
| same-GPU clean/VAE overlap | rejected; zero overlap, worse P95 |

Not tested in this pass by design:

- TeaCache / MagCache
- sparse attention
- KV quantization
- three-step sampling
- custom kernels

## Current strategic baseline

The selected exact working baseline should combine two independently accepted changes:

1. **384×672 native geometry**
2. **decode-first clean-KV scheduling (B)**

The experiments reported 384×672 using A-order, so the combined 384+B result still needs to be measured as an integrated production baseline.

Using the measured 384 DiT total (~0.881 s) only as a rough guide, one clean pass is approximately 0.17–0.18 s if the five forwards are similar. Therefore a combined 384+B first-new-RGB latency around **1.53–1.55 s** is a reasonable hypothesis, not yet a measurement. First action-conditioned RGB would then be roughly **1.66–1.68 s** under the current +125 ms presentation criterion.

Do not record those estimates as achieved results until measured.

## What remains

The large exact implementation pathologies are now mostly exhausted at the selected geometry. Further movement toward ~1.5 s action-conditioned latency likely requires one of:

- stacking the already accepted decode-first schedule with 384×672,
- reducing denoising work (e.g. a principled 3-step sampling experiment),
- another meaningful native-resolution reduction if quality permits,
- an approximate/model-aware reuse method,
- a custom attention or VAE kernel with enough measured headroom to justify maintenance,
- or a different model/decoder architecture.

The next experiment should first establish the combined **384×672 + B-order** production baseline. After that, the most direct remaining ~150–200 ms-class algorithmic lever is a principled three-denoise-step A/B with long-horizon world-stability validation.
