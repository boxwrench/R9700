# Open Documentation Question: `W4A4` vs `W4A16_NVFP4`

**Status:** RESOLVED WITH DIRECT EVIDENCE — both labels are correct, about different things.
**Date:** 2026-08-17
**Blocking B1?** No.

The two labels were recorded as conflicting during the model-acquisition step:

| Source | Label |
|---|---|
| `RadixArk/Qwen3.8-27B-NVFP4` model card | mixed NVFP4 **W4A4** recipe |
| ROCmFPX commit `5290625` | **W4A16_NVFP4** |

They are not in conflict. One describes the **checkpoint**, the other describes
**how llama.cpp executes it**.

---

## Evidence 1 — the checkpoint is W4A4

`SOURCE FACT`. `/ai/models/Qwen3.8-27B-NVFP4/config.json`, `quantization_config.config_groups`:

| Group | Weights | Input activations | Targets |
|---|---|---|---|
| `group_0` | 8-bit float | 8-bit float, `dynamic: false` | 208 |
| `group_1` | **4-bit float, `group_size: 16`** | **4-bit float, `dynamic: false`** | 193 |

`quant_method: modelopt`. `hf_quant_config.json` reports
`quant_algo: MIXED_PRECISION`, `kv_cache_quant_algo: FP8`.

The 193 `group_1` tensors declare `num_bits: 4` for **input activations** as well
as weights. The checkpoint is therefore genuinely W4A4 (statically calibrated —
`dynamic: false`, which is why every quantized tensor ships an `.input_scale`).
The model card's label is accurate. The 193/208 split matches
`tensor-audit.json` exactly.

## Evidence 2 — llama.cpp executes it as W4A16

`SOURCE FACT`. The `.input_scale` tensors are loaded
(`src/llama-model.cpp:1367-1421`, `:1445-1447`) but **no graph consumes them**.
A search for `_in_s` across `src/models/` and `src/llama-graph.cpp` returns two
hits, both `ssm_in_s` — a *weight* scale whose name merely ends in the same
characters. There is no consumer of `output_in_s` or of any `*.input_scale`.

`SOURCE FACT` (runtime). A `llama-eval-callback` dump of the full decode graph
(uniform model, Vulkan1, 40,633 lines) contains **zero** references to
`input_scale`. Activations entering the head are `f32`:

```
node_3847     = (f32) MUL_MAT(output.weight{5120, 248320}, result_norm{5120, 1})
result_output = (f32) MUL(node_3847{248320}, output.scale{1})
```

Weights are 4-bit; activations are 16/32-bit. That is W4A16. ROCmFPX's label is
accurate for the code path that actually runs.

## Consequence

`INFERENCE` — not measured. The weights were calibrated under an assumed 4-bit
activation quantizer that is not applied at inference. Removing a quantizer from
the activation path removes its error, so W4A16 execution of a W4A4 checkpoint
should be *at least* as accurate as the recipe intends, not less. This is a
structural argument, not a perplexity measurement, and is not evidence about
the reference hardware's (Blackwell/SGLang) numerics.

The unused `.input_scale` tensors cost file size and load bandwidth: 193 F32
scalars, negligible in bytes, but they are the reason the tensor count is
1252 rather than 1059 and the reason `output.scale`/`output.input_scale` had to
be claimed explicitly (`src/llama-model.cpp:1425-1447`).

## Recommended wording

Do not write "this is a W4A4 model" or "this is a W4A16 model" unqualified.
Write: **a W4A4 ModelOpt checkpoint executed as W4A16 by llama.cpp, which
ignores the static activation scales.**
