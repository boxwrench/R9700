## 2. Fixed configuration (identical across all four arms)

```
--device Vulkan1 -ngl 99 --no-mmap
-c 4096 -b 512 -ub 512 -fa on -ctk q4_0 -ctv q4_0
--temp 0 --seed 1234 -n 128 --ignore-eos
-no-cnv -st --no-display-prompt --simple-io --verbosity 3
-p "Explain why quantization speeds up large language model inference."
```

Prompt = 64 tokens, generation = exactly 128 tokens in every one of the 32 runs
(`--ignore-eos` guarantees the token count; no run terminated early).

MTP arms add, verbatim from upstream's own
`scripts/check-rocmfp4-qwen-mtp-regression.sh`:

```
--spec-type draft-mtp --spec-draft-device Vulkan1 --spec-draft-ngl all
--spec-draft-n-max 4 --spec-draft-n-min 0 --spec-draft-p-min 0.0 --spec-draft-p-split 0.10
--spec-draft-type-k q4_0 --spec-draft-type-v q4_0
```

`n_max`/`p_min` were **not** tuned. One MTP configuration was used for both models.

**Recorded deviations from upstream's reference script**, both deliberate:

1. `--temp 0` instead of upstream's `--temp 0.2 --top-k 20 --top-p 0.9`, because
   B1 requires deterministic repeatability.
2. `-c 4096` instead of upstream's `-c 262144`, which does not fit alongside a
   28.2 GB model on 34 GB of VRAM.
3. Backend is Vulkan, not upstream's `ROCm0`/`HSA_OVERRIDE_GFX_VERSION=11.5.1`
   (that override targets Strix Halo gfx1151 and is meaningless here).

`--verbosity 3` was chosen over `-v` after measuring that `-v`'s per-draft debug
logging cost ≈3% of MTP decode throughput (43.31 vs 44.61 tok/s on a pilot run).
`--verbosity 3` still emits the full perf and acceptance statistics.

## 3. Protocol

1 unreported warmup + **7 measured repetitions** per arm, 32 runs total, all
`rc=0`. Model load happens inside each repetition but is excluded from decode
throughput — `eval time` counts only the 128 generated tokens. Cold load is
reported separately in §7.

## 5. Correctness and sanity

Determinism was checked on a **separate probe** with stdout and stderr written to
different files (the timing driver merges them, which interleaves log records
into the generated text and makes naive comparison useless). 3 repetitions per
arm:

| Arm | distinct outputs / 3 | verdict |
|---|---|---|
| MIXED SERIAL | 1 | deterministic |
| MIXED MTP | 1 | deterministic |
| UNIFORM SERIAL | 1 | deterministic |
| UNIFORM MTP | 1 | deterministic |

The only byte that varies between repetitions of an arm is the `[ Prompt: … ]`
throughput banner.

* Output is coherent, on-topic, well-formed prose in all four arms.
* No NaN/inf warnings, no malformed output, no degenerate repetition.
* No unexpected EOS — `--ignore-eos` was in force and all 32 runs produced
  exactly 128 tokens.
* Mixed and uniform outputs differ from each other, as expected: uniform
  quantization changes 312 tensors' weights. This is **not** treated as a defect.

### MTP committed output vs same-model serial output — DIVERGES

`MEASURED`. Under greedy settings, MTP committed output does **not** match the
same model's serial output:

| Comparison | common prefix |
|---|---|
| MIXED MTP vs MIXED SERIAL | 1246 / 1505 chars |
| UNIFORM MTP vs UNIFORM SERIAL | 1017 / 1447 chars |

This is documented upstream behaviour at default settings, not a surprise.
`tools/server/server-context.cpp:865-866` prints, for exactly this
configuration:

> `Qwen MTP strict verification is disabled; greedy output may diverge from no-spec decoding (enable --spec-mtp-strict-qwen)`

`--spec-mtp-strict-qwen` defaults to **disabled** (`common/common.h:351`).

### Follow-up: `--spec-mtp-strict-qwen` does not restore equivalence here

Enabling the flag at `-n 128` changed **nothing** — byte-identical output,
identical acceptance counters (51 rounds, 199/75 tokens, identical per-position
rates), decode 37.69 vs 37.26 tok/s. The flag was confirmed active; the run logs
`Qwen strict MTP: boundary-safe multi-row verification with bounded recurrent
rollback is enabled for exact greedy output`.

`SOURCE FACT`. The mitigation is narrow. `server-context.cpp:2485-2496`:

> *"Dense-attention KV width is padded in 256-cell blocks. A verification batch
> that straddles a block makes its earlier rows use a wider ROCm reduction than
> serial decoding and can change greedy output through rounding. […] cap the
> draft so the entire verification stays in one block."*

`INFERENCE`, then **tested**: a 64-token prompt plus 128 generated tokens is 192
positions and never straddles a 256-cell block, so the cap never binds. Re-running
at `-n 400` (464 positions, crossing the boundary) confirms it:

| Comparison at `-n 400` | common prefix |
|---|---|
| MTP default vs serial | 1017 |
| MTP strict vs serial | 1017 |
| MTP strict vs MTP default | **2356** |

The flag demonstrably does take effect — but only from char 2356, well past the
first divergence at char 1017. **The first MTP/serial divergence occurs before
any block straddle and therefore has a different cause than the one the flag
mitigates.**

**Cause: `UNRESOLVED`.** Upstream's comment identifies reduction-width
differences between multi-row verification and single-row decoding as a
mechanism that can flip greedy output through rounding, and that mechanism is a
plausible candidate here — but the comment describes *ROCm* reduction behaviour
and these runs are on *Vulkan/RADV*, whose kernels have their own shapes. It has
not been isolated, and per the benchmark contract it stays `UNRESOLVED` rather
than being attributed. **The measurement that would settle it:** dump target
logits at the divergent position under single-row serial decoding and under
multi-row verification and compare the top-2 gap against the difference between
the two logit vectors.

This does not affect any throughput number in §4, but it does mean the MTP arms
are **not** target-equivalent decoders at these settings, and the MTP figures
should never be presented as "same output, faster".

## 6. Interpretation

**UNIFORM is the primary configuration.** It wins on every axis measured:

* **+34.5% serial decode** (27.33 vs 20.32 tok/s) and **+21.3% MTP decode**
  (37.26 vs 30.71).
* **+42.7% prompt processing** serial (193.96 vs 135.91).
* **10.5 GB less VRAM** (14.7 vs 25.2 GiB serial), which is the difference
  between comfortable and marginal on a 34 GB card.
* Slightly *better* speculative acceptance (1.470 vs 1.442 accepted drafts per
  round).

There is no axis on which mixed is preferable, and no measurement here supports
keeping the 28.2 GB file for inference.

Two observations recorded without causal claims:

* **The MTP multiplier is lower on uniform (1.363) than on mixed (1.511) even
  though uniform's acceptance is slightly higher.** Both facts are `MEASURED`.
  The multiplier is a ratio against a faster baseline, so a smaller multiplier
  here is not a smaller absolute gain — uniform MTP is still the fastest arm.
  No mechanism is asserted.
* **Prompt processing is slower with MTP enabled in both models** (135.91 → 114.60;
  193.96 → 152.96), around −21%. `MEASURED`. Not investigated in B1.

### Relation to previously reported figures

* The earlier `27.9 tok/s` smoke figure is superseded. It was a single un-warmed
  interactive run and was never a benchmark result. It happens to sit close to
  the measured `27.33 ± 0.03` uniform serial figure; that is not a validation of
  it.
* The **~72 tok/s R9700 figure attributed to Charlie remains UNSUBSTANTIATED**
  and is not reproduced here. The fastest arm measured is 37.26 tok/s. Nothing
  in B1 explains a 2× gap, and B1 makes no claim about that figure — the
  configuration behind it is still unknown.
* Upstream's `5290625` "18.3 → 29.5 t/s with MTP" is a **gfx1151** mixed→uniform
  comparison and is not comparable to any number in this table.
