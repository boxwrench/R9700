## GATE 1 — lm_head scale correctness

**Verdict: SOURCE VERIFIED and RUNTIME VERIFIED** for the serial/target decode path.

The gate exists because upstream commit `7b02624` records that a model can emit
plausible text while output scaling is numerically wrong.

### Source chain

1. **Conditional request.** `src/llama-model.cpp:1440`
   `const bool output_has_scales = output && output->type == GGML_TYPE_NVFP4;`
   then `:1442-1447` claims `output.scale` and `output.input_scale` as
   `TENSOR_NOT_REQUIRED`. The comment at `:1425-1439` explains the request must
   *not* be unconditional, because synthesized models materialize any requested
   tensor and would invent a random lm_head scale.
2. **Graph construction.** `src/models/qwen35.cpp:227`
   `cur = build_lora_mm(model.output, cur, model.output_s);` — the scale is
   passed into the output matmul.
3. **Application.** `src/llama-graph.cpp:1188-1192`
   `res = ggml_mul_mat(...); if (w_s) { res = ggml_mul(ctx0, res, w_s); }` —
   applied post-matmul, scalar broadcast.

### Runtime chain

`llama-eval-callback`, uniform model, `--device Vulkan1 -ngl 99`, unmodified
release binary (`build-vulkan/bin/llama-eval-callback`). Final two graph nodes:

```
node_3847     = (f32) MUL_MAT(output.weight{5120, 248320, 1, 1}, result_norm{5120, 1, 1, 1}) = {248320, 1, 1, 1}
    [  83888.8672,   18000.4277,   13199.4785, ...,  -33551.5508,  -38262.0742 ]
    sum = -5552265216.000000

result_output = (f32) MUL(node_3847{248320, 1, 1, 1}, output.scale{1, 1, 1, 1}) = {248320, 1, 1, 1}
    [     10.6670,       2.2889,       1.6784, ...,      -4.2663,      -4.8653 ]
    sum = -705990.875000
```

`MEASURED`. The GGUF value of `output.scale` is `0.00012716`.
`83888.8672 × 0.00012716 = 10.667` — matches the emitted `result_output` to the
printed precision. The scale is loaded from the file (not fabricated), is
consumed by the Vulkan execution path, and produces logits of correct
magnitude. Unscaled logits would be ~8.4e4; this failure mode would not have
been subtle here.

No diagnostic build was required, and no modified binary was used for anything.

### Finding 1 — `.input_scale` is loaded and never used

`SOURCE FACT`. Every `*_in_s` tensor, including `output_in_s`, is loaded and has
**no graph consumer**. A search for `_in_s` across `src/models/` and
`src/llama-graph.cpp` returns two hits, both `ssm_in_s` — a weight scale whose
name merely ends in the same characters. The runtime graph dump contains zero
references to `input_scale`.

This is not a defect; it is what makes the checkpoint execute as W4A16. See
[`../upstream-audit/2026-08-17-w4a4-vs-w4a16.md`](../upstream-audit/2026-08-17-w4a4-vs-w4a16.md).

### Finding 2 — the MTP draft head omits the lm_head scale

`SOURCE FACT`. The two output heads in `src/models/qwen35.cpp` are asymmetric:

| Line | Path | Call |
|---|---|---|
| 227 | main / target | `build_lora_mm(model.output, cur, model.output_s)` |
| 629 | MTP draft head | `build_lora_mm(head_w, cur)` — **no scale** |

`SOURCE FACT`. Line 627 selects
`head_w = layer.nextn.shared_head_head ? … : model.output`. This GGUF has only
four `blk.64.nextn.*` tensors (`eh_proj`, `enorm`, `hnorm`, `shared_head_norm`)
and **no** `shared_head_head.weight`, so `head_w` resolves to `model.output` —
an NVFP4 tensor that does carry a scale. The scale is simply not passed.

**Impact under the B1 configuration: none.** `output.scale` is a single positive
scalar, and `argmax` is invariant under multiplication by a positive constant.
B1 runs `--temp 0` with `--spec-draft-p-min 0.0`, so no probability magnitude
enters either drafting or acceptance, and draft token identity is unaffected.

**This is not a general safety claim.** Under settings that consume
probabilities the omission is consequential, because unscaled logits are ~8.4e4
and saturate the softmax. Upstream's own reference script
`scripts/check-rocmfp4-qwen-mtp-regression.sh` runs `--temp 0.2 --top-k 20
--top-p 0.9`, which does consume them. Whether that materially degrades
acceptance there is **UNRESOLVED — not measured by B1**, and is recorded as a
candidate upstream finding, not a confirmed defect.

### Provenance

`SOURCE FACT`. The mixed GGUF carries exactly **193** NVFP4 tensors, matching
`tensor-audit.json` (`NVFP4: 193`, `FP8: 208`, `unchanged: 798`,
`mtp_tensor_count: 15`) and matching upstream commit `5290625`'s statement that
all 193 original NVFP4 tensors were verified bit-exact. The tensor count 1252
matches the "expected 1252" in commit `7b02624`'s load-error text. This is the
same checkpoint upstream tested.

Note the MTP accounting differs by representation: `tensor-audit.json` counts 15
MTP tensors in the HF checkpoint; the GGUF exposes 4 `blk.64.nextn.*` tensors.
The remainder are folded into the ordinary `blk.64.*` layer tensors by the
converter. This is a representation difference, not a loss — `INFERRED` from the
tensor listing, not separately verified.

### Uniform conversion — the original NVFP4 tensors were not requantized

`MEASURED`. Every one of the 193 tensors that was NVFP4 in the mixed file was
compared byte-for-byte (SHA256 of raw tensor data) against the same tensor in
the uniform file:

```
originally-NVFP4 tensors: 193
BIT-EXACT: 193   DIFFERENT: 0   MISSING: 0
scale/input_scale tensors: 386  identical: 386
```

`llama-quantize` passed the pre-quantized NVFP4 tensors through untouched and
left all 386 scale tensors identical. The size reduction comes only from the
312 BF16 tensors converted to NVFP4 and `token_embd` converted to Q5_K
(313 BF16 → 312 NVFP4 + 1 Q5_K; 193 + 312 = 505 NVFP4, as observed).

This independently reproduces upstream's bit-exactness claim on our own
conversion, on gfx1201, rather than accepting the commit message.

**Verdict: GATE 2 PASSED.**
